# Kira Desktop

**Техническая спецификация:** v0.1 (Draft)  
**Целевая платформа:** NixOS / Linux / Wayland  
**Основа:** Niri Wayland Compositor  
**Статус:** идёт bootstrap: созданы Rust Workspace, Core, IPC, Shell Host и Svelte-превью; типизированный WebKit ↔ Core bridge работает, панель визуально проверена во вложенном Niri; Niri IPC и Event Bus ещё не подключены; MVP не готов.

## 1. Цель проекта

Kira Desktop — современное, высокопроизводительное, модульное, декларативное и расширяемое окружение рабочего стола, построенное на Rust и Svelte 5.

Основные требования:

- Декларативная конфигурация через KDL.
- Модульная архитектура и независимые компоненты.
- Пользовательские виджеты и расширения на Svelte 5 / TypeScript.
- Горячая перезагрузка конфигурации и компонентов, где это технически возможно.
- **Премиальная дизайн-система:** визуальная целостность, типографика и качество деталей обязательны для всех поверхностей и виджетов.
- Единая дизайн-система и настраиваемые темы.
- Минимальное потребление ресурсов и высокая отзывчивость.
- Независимость системного ядра от пользовательского интерфейса.
- **NixOS-first:** разработка, сборка и поставка проекта ориентированы прежде всего на NixOS.

## 2. Технологический стек

| Слой | Технологии |
| --- | --- |
| Compositor | Niri |
| Backend | Rust, Tokio |
| Frontend | Svelte 5, TypeScript, Vite |
| UI Components | shadcn-svelte, Tailwind CSS |
| WebView | GTK4, WebKitGTK 6 |
| Wayland | gtk4-layer-shell |
| IPC | Unix Domain Socket, JSON-RPC |
| Configuration | KDL |
| Serialization | Serde |
| System Integration | Niri IPC, D-Bus, PipeWire |
| Build | Cargo Workspace, Vite |
| NixOS build / development | Nix Flakes, `flake.nix`, `nix/package.nix` |
| Task runner | Taskfile (`go-task`) |
| CI | GitHub Actions |

Frontend собирается в статические ресурсы и загружается через WebKitGTK. Tauri, Node.js-сервер и Lua **не используются в runtime**. Node.js допустим только на этапе разработки и сборки frontend.

## 3. Архитектура

Система состоит из двух основных процессов.

### Kira Core (Rust Daemon)

- Управление системным состоянием.
- Интеграция с Niri.
- Управление конфигурацией и расширениями.
- Системные сервисы и Event Bus.
- Предоставление типизированного IPC API.

### Kira Shell (Rust Host + Svelte UI)

- Создание Wayland layer-shell поверхностей.
- Отображение Svelte-компонентов через WebKitGTK.
- Управление панелями, доком и рабочим столом.
- Связь с Kira Core через Unix Domain Socket.

**Схема взаимодействия:**

```text
Svelte UI ↔ WebKit Bridge ↔ Rust Host ↔ Unix Socket ↔ Kira Core ↔ Niri / Linux
```

Kira Core является единым источником системного состояния. UI подписывается на изменения и отправляет команды через типизированный API.

## 5. Декларативная конфигурация

Конфигурация хранится в `~/.config/kira-desktop/` в формате KDL.

Пример:

```kdl
theme "dark" {
    accent "#fca311ff"
    radius 12
}

surface "topbar" {
    layer "top"
    height 42

    left {
        widget "workspaces"
        widget "launcher"
    }

    center {
        widget "clock"
    }

    right {
        widget "system-tray"
        widget "audio"
    }
}
```

**Требования:**

- Валидация конфигурации до применения.
- Hot Reload без перезапуска оболочки, где это технически возможно.
- Сохранение предыдущего работоспособного состояния при ошибке.
- Настройки виджетов через единый механизм.
- Возможность переопределения стандартных настроек.

## 6. Система виджетов и расширений

Все встроенные и пользовательские виджеты разрабатываются на Svelte 5.

**Widget SDK** предоставляет:

- Доступ к системному состоянию через типизированный API.
- Подписки на события.
- Команды управления Niri.
- Доступ к темам и UI-компонентам.
- Хранение пользовательских настроек.
- Управление жизненным циклом виджета.

Сторонние виджеты распространяются в виде предварительно собранных JS-модулей с манифестом, версией SDK и декларацией необходимых разрешений.

В первой версии поддерживаются **доверенные** пользовательские расширения. Декларация разрешений сама по себе не является изоляцией. Выполнение недоверенных плагинов требует отдельного механизма (например, отдельных изолированных WebView) и не входит в MVP.

## 7. Инженерные принципы

- **KISS:** минимальное количество абстракций, процессов и зависимостей.
- **DRY:** общие типы, SDK, компоненты и бизнес-логика без дублирования.
- **SOLID:** чёткие границы ответственности, явные интерфейсы, зависимости от контрактов, а не реализаций.
- **Pragmatic Engineering:** простые работающие решения важнее преждевременных обобщений.
- **Modular Composition:** функциональность собирается из независимых заменяемых компонентов с минимальной связанностью.

Дополнительные требования:

- Композиция предпочтительнее наследования и монолитных структур.
- Типизированные ошибки и явная обработка отказов.
- Минимизация глобального изменяемого состояния.
- Стабильные версионированные контракты IPC и Widget SDK.
- Возможность тестирования модулей без запущенного Niri.

## 8. NixOS: разработка, сборка и доставка (обязательное требование)

**NixOS — основная целевая система.** Поддержка других Linux-дистрибутивов возможна в будущем, но не является критерием MVP.

Репозиторий **обязан содержать**:

1. `flake.nix` — декларацию Nix Flake с воспроизводимой средой разработки (`devShells`), проверками (`checks`) и, после появления исходного кода приложения, собираемым пакетом (`packages.default`).
2. `nix/package.nix` — отдельное Nix-выражение для сборки и упаковки Kira Desktop. Nix-сборка должна собирать Rust Core/Shell и production frontend, устанавливать UI-ресурсы и обеспечивать необходимые GTK4/WebKitGTK/Wayland зависимости.
3. `flake.lock` — зафиксированные входные зависимости Flake; файл добавляется и поддерживается после первого `nix flake lock`.

Требования к Nix-сборке:

- Разработка — через `nix develop`; сборка — через `nix build`; проверка Flake — через `nix flake check`.
- Результат финальной сборки — installable-пакет приложения, а не только архив исходников или документации.
- Сборка frontend и backend воспроизводима, зависимости фиксируются lock-файлами; обращение к сети из build sandbox не допускается.
- Системные библиотеки и build-time инструменты объявляются явно; глобально установленные Node.js/Rust не должны быть обязательны в Nix-окружении.
- Приложение должно устанавливаться и запускаться в NixOS с Niri; интеграция с NixOS-модулем может появиться отдельно, без преждевременного усложнения структуры.

**Текущий статус реализации:** Rust Workspace, frontend, lock-файлы и Nix-пакет добавлены. `nix build` и нативная компиляция `kira-shell` прошли GitHub Actions на Linux с зафиксированными зависимостями. Графический запуск и визуальная проверка панели во **вложенной оконной сессии Niri** подтверждены вручную; полноценная системная установка и интеграционные E2E-тесты пока не выполнены. Это не означает готовность MVP: Niri IPC, KDL и система виджетов ещё не реализованы.

## 9. Taskfile: единый интерфейс команд (обязательное требование)

Команды проекта централизуются в корневом `Taskfile.yml` с использованием [Task](https://taskfile.dev/). CI по возможности вызывает **те же** задачи, что доступны локально, без дублирования логики.

Предусмотренные задачи:

| Команда | Назначение |
| --- | --- |
| `task check` | Комплексная проверка репозитория |
| `task spec:check` | Наличие обязательной документации и Nix/CI-файлов |
| `task fmt` | Проверка форматирования Rust |
| `task lint` | Clippy и статическая проверка Svelte/TypeScript |
| `task test` | Rust unit/integration и frontend component tests |
| `task build` | Локальная production-сборка (когда исходники готовы) |
| `task nix:check` | `nix flake check` |
| `task nix:build` | `nix build` |

Taskfile должен ясно указывать, какие проверки ещё нельзя запустить до появления соответствующих исходников. **Отсутствие кода нельзя считать успешно протестированным кодом.** Команды сборки должны возвращать ошибку до появления необходимой структуры.

## 10. Тестирование и качество

- **Unit Tests:** конфигурация, бизнес-логика, обработчики команд.
- **Integration Tests:** IPC, сервисы, взаимодействие между крейтами.
- **Contract Tests:** соответствие Rust API и TypeScript SDK.
- **Component Tests:** Svelte-компоненты и пользовательские виджеты.
- **E2E Tests:** запуск оболочки и поверхностей в тестовой Wayland-сессии.

По мере реализации CI должен выполнять:

- `cargo fmt --all -- --check`;
- `cargo clippy --workspace --all-targets -- -D warnings`;
- `cargo test --workspace --all-targets`;
- проверку TypeScript/Svelte;
- тесты frontend;
- production-сборку frontend и проекта.

**Лёгкий CI обязателен** в `.github/workflows/ci.yml` на `push` и `pull_request`. Начальный GitHub Actions workflow выполняет `task check`, всегда валидирует структуру спецификации и условно активирует Rust/frontend-проверки после появления соответствующих компонентов. Тяжёлые NixOS/Wayland E2E-тесты можно вынести в отдельный этап, не утяжеляя базовый CI.

Frontend должен предоставлять npm scripts `check`, `test:ci`, `build`, которые вызываются Taskfile. CI не должен притворяться, что Rust/frontend-тесты уже выполняются до появления исходного кода.

## 11. MVP

Первая версия должна включать:

1. Rust Core и Shell Host.
2. Unix Socket IPC и типизированный Svelte SDK.
3. KDL Config Engine с Hot Reload.
4. Top Bar и Workspaces.
5. Application Launcher.
6. Dock и Clock.
7. Премиальную дизайн-систему и темы с обязательной палитрой по умолчанию (раздел 15).
8. Загрузку пользовательских Svelte-виджетов.
9. Автоматизированные тесты основных компонентов.
10. Сборку и запуск на NixOS через Nix Flake.
11. Taskfile и работающий лёгкий CI.

## 12. Критерии готовности MVP

- Shell запускается поверх Niri на NixOS без Tauri.
- Панель корректно использует Wayland layer-shell.
- Изменение KDL обновляет UI без полной перезагрузки процесса.
- Системные события передаются из Rust в Svelte.
- Пользовательский виджет устанавливается без пересборки Kira Desktop.
- Ошибка отдельного виджета не должна приводить к завершению Kira Core.
- Критическая системная логика покрыта автоматизированными тестами.
- `nix build` создаёт запускаемый пакет с собранным frontend; `nix develop` предоставляет все build-time инструменты.
- `task check` и CI выполняют реальные тесты добавленных Rust/TypeScript компонентов.
- Стандартные поверхности и виджеты соответствуют дизайн-системе раздела 15: премиальное визуальное качество, семантические токены, читаемость, клавиатурная навигация и reduced motion.

## 13. Главный архитектурный принцип

*Kira Desktop — это не монолитное приложение, а композиция независимых системных сервисов и интерфейсных компонентов.*

**Rust отвечает за возможности системы. Svelte 5 отвечает за интерфейс. KDL определяет декларативное состояние рабочего стола. Nix обеспечивает воспроизводимую разработку и поставку для NixOS.**


## 14. Безопасное локальное превью (Developer Experience)

Разработка и проверка поверхностей выполняются без замены основного рабочего
окружения через команду `task dev:preview`.

- Превью использует вложенный Niri в оконном режиме с временной KDL-конфигурацией.
- Shell получает только фактический Wayland-дисплей дочернего Niri.
- Core использует отдельный IPC-сокет, задаваемый `KIRA_CORE_SOCKET`.
- GTK Host использует отдельный экземпляр приложения при `KIRA_PREVIEW=1`.
- Завершение превью останавливает только его собственные процессы.
- Команда не выполняет `nixos-rebuild switch`, не меняет системные службы
  и не редактирует настройки основного Niri.
- Изоляция ограничена композитором и процессами. Это не полноценная VM.

Подробная инструкция: [PREVIEW.md](PREVIEW.md).

## 15. Премиальный UI и фирменная палитра (обязательное требование)

### 15.1. Визуальный характер

**Kira Desktop должен выглядеть премиально:** современно, сдержанно,
элегантно, цельно и внимательно к деталям. Это обязательный критерий
качества, а не необязательное дизайнерское пожелание.

- **Чистая визуальная иерархия.** Основные действия и системное состояние
  читаются сразу, вторичные элементы не перегружают экран.
- **Единый ритм.** Базовый шаг отступов 4 px, предпочтительно кратные
  8 px; согласованные радиусы, высоты, выравнивание и размеры элементов.
- **Типографика.** Разборчивые шрифты, ограниченное количество начертаний,
  аккуратные интервалы, продуманная иерархия.
- **Материалы и глубина.** Сдержанные поверхности, деликатные границы,
  тени и полупрозрачность лишь при наличии функциональной пользы. Никакого
  декоративного шума и злоупотребления blur/градиентами.
- **Плавность.** Короткие, ненавязчивые переходы, ориентир 120–220 мс;
  обязательно учитывать `prefers-reduced-motion`.
- **Согласованность.** Top Bar, Dock, Launcher, уведомления, меню,
  настройки и виджеты образуют одну дизайн-систему со всеми состояниями:
  default, hover, focus, active, disabled, loading, error.
- **KISS.** Минимум необходимой сложности: понятные функции, явные состояния,
  отсутствие дополнительных уровней абстракции ради самих абстракций.
- **DRY.** Общие дизайн-токены и одинаковая инфраструктура живут в одном
  месте; различающуюся логику компонентов не объединять искусственно.
- **Практичность.** Премиальный вид не может ухудшать отзывчивость,
  доступность, контрастность или клавиатурное управление.

### 15.2. Каноническая палитра Kira Default

По умолчанию используется **тёмная тема Kira Default** из **ровно пяти**
базовых цветов с непрозрачным альфа-каналом `ff`, заданных владельцем проекта:

| Имя | HEX RGBA | RGB | Назначение |
| --- | --- | --- | --- |
| **Black** | `#000000ff` | `rgb(0, 0, 0)` | Главный фон и текст на оранжевых элементах |
| **Prussian Blue** | `#14213dff` | `rgb(20, 33, 61)` | Поверхности, структура |
| **Orange** | `#fca311ff` | `rgb(252, 163, 17)` | Выделение, активные элементы, фокус |
| **Alabaster Grey** | `#e5e5e5ff` | `rgb(229, 229, 229)` | Вторичный текст и границы |
| **White** | `#ffffffff` | `rgb(255, 255, 255)` | Основной текст на тёмном фоне |

Каноническая машинно-читаемая запись:

```json
{
  "Black": "#000000ff",
  "Prussian Blue": "#14213dff",
  "Orange": "#fca311ff",
  "Alabaster Grey": "#e5e5e5ff",
  "White": "#ffffffff"
}
```

CSV, массивы, XML и другие формы являются представлениями **той же**
палитры. Базовые цвета в компонентах не хардкодятся. Дополнительные оттенки
разрешены только как вычисляемые смеси/прозрачности этих пяти значений.
Пользовательские переопределения темы через KDL остаются будущей задачей.

### 15.3. Семантические токены

Все компоненты обязаны использовать семантические CSS-переменные.
В дополнение к исходным `--black`, `--prussian-blue`, `--orange`,
`--alabaster-grey` и `--white` определены роли:

| CSS-токен | Значение в Kira Default | Роль |
| --- | --- | --- |
| `--kira-color-background` | `var(--black)` | Фон |
| `--kira-color-surface` | `var(--prussian-blue)` | Поверхности |
| `--kira-color-muted` | `var(--alabaster-grey)` | Вторичный текст |
| `--kira-color-accent` | `var(--orange)` | Выделение и фокус |
| `--kira-color-text` | `var(--white)` | Основной текст |
| `--kira-color-on-accent` | `var(--black)` | Контрастный текст на Orange |
| `--kira-color-earth` | `var(--prussian-blue)` | Совместимый псевдоним |

Для hover, border, disabled и overlay допустимы производные оттенки.
GTK Launcher использует ту же палитру через именованные цвета CSS.

### 15.4. Контрастность и доступность

Примеры сочетаний (WCAG, относительные контрастные отношения):

| Текст / фон | Контраст | Применение |
| --- | --- | --- |
| White / Black | **21.00:1** | Основной текст |
| White / Prussian Blue | **15.97:1** | Основной текст на поверхности |
| Alabaster Grey / Black | **16.67:1** | Вторичный текст |
| Alabaster Grey / Prussian Blue | **12.68:1** | Вторичный текст на поверхности |
| Orange / Black | **10.39:1** | Акцент на фоне |
| Orange / Prussian Blue | **7.90:1** | Акцент на поверхности |
| Black / Orange | **10.39:1** | Текст на активном workspace |

**White / Orange** имеет контраст всего **2.02:1**; на оранжевых
элементах используется чёрный текст, не белый.

Критерии приёмки:

- Контраст обычного текста не ниже **4.5:1**, крупного текста и
  значимых нетекстовых элементов управления не ниже **3:1** там,
  где соответствуют требованиям WCAG.
- Активное состояние, выбор и фокус различимы **не только цветом**.
- Клавиатурная навигация, видимый focus indicator, корректные
  состояния элементов и `prefers-reduced-motion` обязательны.
- Финальные поверхности проходят визуальную проверку во вложенном
  Niri при различных размерах и масштабах дисплея. Успешный CI сам
  по себе не подтверждает премиальный визуальный результат.

**Статус реализации:** фирменные токены Kira Default, Top Bar на Svelte 5 +
Tailwind CSS v4, нативные GTK Launcher и собственный Calendar Picker
реализованы. Внедрена базовая клавиатурная навигация. Это **не означает
завершённой визуальной приёмки**: проверка размеров, масштабов,
локализации и всех интерактивных состояний остаётся открытой. Dock,
уведомления, настройки и пользовательские темы относятся к будущим этапам.
